# v300 Qwen 3.6 Router Baseline Lock

This document describes the v300 baseline-lock procedure for the Qwen 3.6
router served on the WSL1 multi-GPU lane. The baseline is the floor against
which v301+ runs ratchet quality and latency.

## Two artifacts, two purposes

| File | What it locks | Generated by |
|------|---------------|--------------|
| `baselines/v300-qwen36-baseline.schema.json` | Corpus contract: 50 prompts, 5 categories, per-prompt quality contracts, JSON report shape | `go run ./cmd/baseline-lock` (Mac, in-process) |
| `baselines/v300-qwen36-baseline.live.json` | Real Qwen 3.6 latency (p50/p95/p99) and quality pass-rate per category | `fleet-bench --mode matrix` (WSL1, against router) |

The schema lock is the **contract**. The live file is the **measurement**.
They are two distinct files so a reviewer never has to guess whether a
number came from a stub server or a real model.

## Schema lock (Mac, deterministic, no model required)

```bash
runx go test --repo fleet-bench -- ./internal/corpus/ ./internal/matrix/
go run ./cmd/baseline-lock          # writes baselines/v300-qwen36-baseline.schema.json
jq '.metadata, .report.aggregate'   # sanity-check the envelope
```

Acceptance:

- `metadata.schema_lock == true`
- `report.aggregate.total == 50`
- `report.aggregate.quality_rate == 1.00` (every prompt's contract is satisfiable)
- 5 categories present: `chat`, `code`, `reasoning`, `summarisation`, `translation`

A failing stub means either a corpus contract changed or a stub fell out of
sync. Edit `cmd/baseline-lock/main.go::stubByID` (or the corpus contract)
and regenerate — never silently lower the threshold.

## Live baseline (WSL1, against the actual Qwen 3.6 router)

Run from the WSL1 host that has `llm-cluster-router` reachable on
`http://127.0.0.1:8001/v1` (or the configured port). The Mac side does not
talk directly to the router because of the no-shell-leak Tier A boundary
(`zd-gateway-boundary.mdc`).

```bash
# On WSL1
cd ~/fleet-bench
go build -o ./bin/fleet-bench ./cmd/fleet-bench
./bin/fleet-bench --mode matrix \
    --corpus v300-baseline \
    --endpoint http://127.0.0.1:8001/v1 \
    --model qwen3.6-instruct \
    --out ./baselines/v300-qwen36-baseline.live.json
```

Acceptance for the live file:

- `report.aggregate.total == 50` (no prompts dropped)
- `report.aggregate.quality_rate >= 0.85` (v300 floor; ratcheted in v301+)
- `report.aggregate.latency_p95_ns < 8e9` (p95 under 8 s on WSL1 RTX 3090)
- 0 status_code != 200 rows (router served every prompt)

A run that misses the floor is a **lock failure**, not a recoverable
soft-fail — it indicates the router (or the corpus) has regressed.

## What the live file must NOT include

- Endpoint URLs containing internal IPs (use the loopback `127.0.0.1` form
  only; the file is committed to a public-mirror-eligible repo).
- API keys, bearer tokens, or any auth material — the matrix runner reads
  `--api-key` at runtime; do not embed it.
- Prompt text — already in the corpus; the live file references prompts
  by `(category, prompt_id)` only.

## Cross-sprint diff (v301+)

The aggregator at `cmd/baseline-diff` (planned for v301) will:

1. Load the v300 live file as the baseline.
2. Load the v301 live file as the candidate.
3. Diff per-category quality_rate and latency p95.
4. Fail the build if quality drops more than 2pp or p95 grows more than 25%.

Until that lands, run the comparison manually with `jq`:

```bash
jq -s '{v300: .[0].report.aggregate, v301: .[1].report.aggregate}' \
    baselines/v300-qwen36-baseline.live.json \
    baselines/v301-qwen36-baseline.live.json
```
